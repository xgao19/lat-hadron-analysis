\section{项目目标与最终产品形态}

\subsection{本项目不是什么}

\begin{itemize}
  \item \textbf{不是普通脚本集合}。不是让学生把几个 notebook 跑通就交差。
  \item \textbf{不是简单聊天机器人}。不是套一个 LLM 对话界面就叫``科研 AI agent''。
  \item \textbf{不是手动流程的自动化 wrapper}。不是只把人工操作换成 shell script。
\end{itemize}

\subsection{本项目是什么}

本项目是一个 \textbf{可复现、可审计、可逐步自主决策的 LQCD meson DA analysis agent system}。目标是把真实的格点 QCD meson DA 数据分析流程尽可能交给 AI agents 自动执行、自动检查、自动复现和自动记录，只在关键决策、风险升级和最终物理结论时才引入人工判断。

系统的五个核心设计目标：

\begin{enumerate}
  \item \textbf{可复现}：所有分析由 config、schema、workflow、日志和版本控制驱动，而不是依赖手动 notebook 操作。
  \item \textbf{可追责}：每一个重要判断都要留下 decision log，包括输入、候选方案、选择理由、风险等级和是否需要人工批准。
  \item \textbf{AI-first automation}：优先让 AI 自动完成重复性、结构化、可检查的科研工程工作。
  \item \textbf{Risk-based human-gated}：按风险等级决定人类介入深度。Low risk 自动推进，Medium risk 推荐复核，High risk 必须审批，Critical risk 禁止 AI 自行推进。
  \item \textbf{真实科研可用}：最终应能让 AI 尽可能承担真实 meson DA 分析中的常规工作，而不是停留在玩具示例。
\end{enumerate}

\subsection{三个月后产品应展示的能力}

三个月结束时，原型系统应能对一个真实 golden example case 展示以下闭环：

\begin{enumerate}
  \item 读取一个 golden example case 的 config 和数据；
  \item 自动完成 data check、analysis run、fit diagnostics、matrix element checks；
  \item 自动生成 plots、\texttt{summary.csv}、\texttt{result.json}；
  \item 多 agent 给出 recommendation 和 objection；
  \item Analysis Coordinator 生成 \texttt{decision\_log.json}；
  \item 低风险自动推进并写入 memory，中高风险生成 approval packet 并触发 Human Approval Gate；
  \item case memory 记录 accepted / rejected / failed cases；
  \item 最终生成一份 human-readable analysis report。
\end{enumerate}

\section{学习目标与技能分类}

本章明确学生三个月的学习目标，按\textbf{三类技能}组织。学生不需要一开始掌握所有内容，但需要在三个月内逐步达到熟练水平。

\subsection{LQCD Analysis 学习目标}

\textbf{需要掌握：}
\begin{itemize}
  \item 理解 2pt correlator 的基本结构和 effective mass 的含义；
  \item 理解 bootstrap / jackknife 的统计原理，能解释为什么需要 binning；
  \item 理解 $\chi^2$/dof 在拟合质量判断中的作用和局限；
  \item 理解 1-state / 2-state / 3-state fit 的物理含义和选择依据；
  \item 理解 fit window（$t_{\min}$ / $t_{\max}$）和 prior 如何影响拟合结果；
  \item 理解 DA ratio 的基本结构，知道 bare matrix element 如何从 ratio 中提取；
  \item 理解 $z$-dependence 和 $P_z$-dependence 的物理意义；
  \item 理解 real/imaginary symmetry 和 normalization condition 的含义。
\end{itemize}

\textbf{不要求一开始掌握：}
\begin{itemize}
  \item 详细的 LQCD 场论推导；
  \item LaMET / factorization / matching 的完整理论；
  \item 多个 ensemble 的 continuum extrapolation；
  \item 完整的 systematic uncertainty budget 估计。
\end{itemize}

\subsection{Software Engineering / Reproducibility 学习目标}

\textbf{需要掌握：}
\begin{itemize}
  \item 把 notebook-style 分析改造成 config-driven Python CLI；
  \item 用 Pydantic 定义输入输出 schema；
  \item 用 pytest 写测试并验收 Codex 生成的代码；
  \item 用 Snakemake 管理文件依赖和增量重跑；
  \item 用 Git 做小步提交（每完成一个模块就 commit）；
  \item 写 manifest、run.log、result.json 以记录 provenance；
  \item 理解 overwrite protection 和 output validation 的重要性。
\end{itemize}

\textbf{不要求一开始掌握：}
\begin{itemize}
  \item Docker / containerization；
  \item CI/CD pipeline；
  \item 复杂的 HPC 调度（SLURM 等）；
  \item 大规模数据管理。
\end{itemize}

\subsection{AI Agent System 学习目标}

\textbf{需要掌握：}
\begin{itemize}
  \item 理解 multi-agent division of labor：每个 agent 有明确职责和边界；
  \item 理解 Risk-Based Autonomy：什么风险等级对应什么自动化程度；
  \item 理解 debate/critic 机制：Critical Referee 如何寻找漏洞；
  \item 理解 decision log 的格式和可追责性要求；
  \item 理解 Human Approval Gate 的触发条件和审批包结构；
  \item 理解 case memory 的结构化存储和检索需求；
  \item 用 LangGraph 或 Python state machine 表达 agent 状态流；
  \item 写 Codex prompt 让 AI 生成代码、测试和文档，并尽量减少人类手工写实现。
\end{itemize}

\textbf{不要求一开始掌握：}
\begin{itemize}
  \item LLM fine-tuning 或 RLHF；
  \item 复杂的 RAG pipeline；
  \item 大规模 agent 系统的运维和监控；
  \item 多用户协作的 agent 系统设计。
\end{itemize}

\section{Risk-Based Autonomy：从全手动到研究驾驶舱}

\subsection{Autonomy Level：AI 自主程度的五个台阶}

本项目的长期目标不是停留在"AI 帮人跑脚本"，而是让 AI agents 逐步承担越来越多的 analysis decisions。下表定义五个自主等级：

\begin{center}
\begin{tabular}{p{0.12\linewidth}p{0.22\linewidth}p{0.56\linewidth}}
\toprule
等级 & 名称 & 含义 \\
\midrule
A0 & Manual & 人类手动完成所有分析步骤；AI 最多提供代码补全。 \\
A1 & AI-assisted coding & 人类用 Codex 生成代码，但仍由人类检查、运行、解释所有结果。 \\
A2 & Semi-autonomous workflow & Snakemake 管理依赖；Analysis Engineer 自动执行 workflow；结构化输出自动生成。人类审查关键结果。 \\
A3 & Risk-based autonomous agent system & 多 agent 分工协作；低风险自动推进，中风险推荐复核，高风险生成审批包。人类只在关键节点介入。 \\
A4 & Research copilot group & AI agents 像一个 LQCD analysis subgroup 一样协同工作；自动承担大部分分析决策；人类主要提出物理目标、审查高风险结论、承担最终责任。 \\
\bottomrule
\end{tabular}
\end{center}

本项目的\textbf{前三个月目标是达到 A2--A3 的初级版本}（A2 在 Month 2 完成，A3 在 Month 3 完成）。长期目标接近 A4。

\subsection{四级风险与对应的人类介入规则}

所有 AI decision 都按风险等级分级处理。Human Approval Gate 不是每一步都要人类审批，而是\textbf{基于风险的、条件触发的 exception path}。

\begin{center}
\begin{tabular}{p{0.12\linewidth}p{0.25\linewidth}p{0.25\linewidth}p{0.28\linewidth}}
\toprule
风险等级 & AI 行为 & 结果状态 & 人类介入 \\
\midrule
Low & 自动执行、自动记录、自动推进 workflow & 自动进入 accepted candidate & \textbf{不需要} \\
Medium & 继续推进 workflow，标记 \texttt{human\_review\_recommended=true} & \texttt{pending candidate}，不能自动升级 & \textbf{建议}复核（非强制） \\
High & 生成 \texttt{approval\_packet}，workflow 在 promotion 前暂停 & \texttt{pending approval} & \textbf{必须} Human Approval Gate 审批 \\
Critical & AI \textbf{不允许}继续推进科学结论 & 系统暂停，等待裁决 & \textbf{必须} Human PI / advisor 亲自决定 \\
\bottomrule
\end{tabular}
\end{center}

\subsection{AI 决策边界：三类权限的明确划分}

\textbf{AI 可以自动决定（无需人类介入）：}
\begin{itemize}
  \item 检测 missing files 并报错
  \item config validation failure 的诊断和提示
  \item routine rerun（参数未变的重复执行）
  \item failed fit 的自动标记和记录
  \item bad candidate fit 的自动拒绝（基于明确的 $\chi^2/\mathrm{dof}$ 或稳定性阈值）
  \item diagnostic plot 的生成和归档
  \item targeted rerun suggestion 的提出
  \item low-risk workflow 的自动推进和 memory update
\end{itemize}

\textbf{AI 可以推荐但不能自动最终批准：}
\begin{itemize}
  \item central fit candidate 的选择
  \item systematic variation set 的定义
  \item data exclusion 的建议（标记 exclusion candidate）
  \item accepted candidate 的 promotion（标记 pending promotion）
  \item physics interpretation 的初步撰写
\end{itemize}

\textbf{必须 Human Approval Gate（不可绕过）：}
\begin{itemize}
  \item final central value 的确定
  \item final systematic uncertainty 的确定
  \item final accepted result 的 promotion（pending $\to$ accepted）
  \item final data exclusion 的确认
  \item paper-level claim 的审批
  \item major analysis strategy change 的批准
  \item overriding Critical Referee 的 major objection
\end{itemize}

\subsection{典型场景：四种风险等级的处理流程}

\begin{enumerate}
  \item \textbf{Good case（Low risk）：}Correlator Analyst 报告 plateau 稳定，Fit Strategy Postdoc 推荐 2-state fit，Critical Referee 无 major objection。Analysis Coordinator 判定 low risk，自动推进，写 decision\_log，更新 accepted memory。人类不需要介入。
  
  \item \textbf{Ambiguous case（Medium risk）：}1-state 和 2-state 结果相差 1.8 sigma，但各自的 fit 质量可接受。Analysis Coordinator 判定 medium risk，标记 pending candidate，推荐人类看一下。Workflow 不阻塞，结果暂时不升级为 final。
  
  \item \textbf{High-stakes case（High risk）：}Critical Referee 提出 major objection：$P_z$ dependence 在归一化后改变趋势。Analysis Coordinator 判定 high risk，生成 approval packet，workflow 在 promotion 前暂停。人类导师审批后决定：接受 2-state 为 central，并要求下一轮检查 $P_z$ systematics。
  
  \item \textbf{Crisis case（Critical risk）：}Critical Referee 发现 local matrix element 违反 normalization condition，且 Fit Strategy Postdoc A 和 B 的基础假设互相矛盾。Analysis Coordinator 判定 critical risk，系统暂停，通知 PI。PI 组织人工 review 后决定方案。
\end{enumerate}

\section{从 TradingAgents 到 LQCD Research Group Agents}

\subsection{借鉴什么：TradingAgents 的核心设计思想}

本项目借鉴了现代 multi-agent 系统（尤其是 TradingAgents）的设计理念。但借鉴的不是金融角色名称，而是背后的\textbf{系统架构思想}：

\begin{itemize}
  \item \textbf{Specialized roles}：不要一个大而全的 agent 做所有事。把分析任务拆成多个有明确边界的角色——执行者、诊断者、策略者、批判者、协调者。
  \item \textbf{Staged decision pipeline}：数据检查 $\to$ 分析执行 $\to$ 诊断评估 $\to$ 批判审查 $\to$ 综合决策 $\to$ 审批 $\to$ 归档。每一步的输出是下一步的输入。
  \item \textbf{Debate / critic}：系统必须设计反方角色，专门寻找漏洞和反例。不能让同一个 agent 既生成结果又自我审查。
  \item \textbf{Risk gate}：所有 decision 都按风险等级分级处理。低风险自动通过，高风险必须人类审批。
  \item \textbf{Memory}：保存结构化经验（accepted / rejected / failed cases），而不是保存聊天记录。为后续分析提供 prior experience。
  \item \textbf{Final decision gate}：最终审批不是"每步都要人类点头"，而是在高风险节点保留人类最终责任。
\end{itemize}

\subsection{Agent 1：Analysis Engineer Agent（L1：工程与执行）}

\begin{tcolorbox}[colback=gray!5,colframe=gray!50,title=真实科研组类比]
会写代码和维护 pipeline 的研究生 / junior postdoc / coder。不是在干"低级 labor"，而是在建设科研基础设施。
\end{tcolorbox}

\textbf{解决的问题：}科研分析不能长期依赖 notebook 里手动改路径、手动运行 cell、手动保存图。必须有可靠、可复现、可测试的工程基础。

\textbf{输入：}
\begin{itemize}
  \item \texttt{configs/<case\_id>.yaml}（Pydantic 验证后）
  \item raw data 路径（只读）
  \item output directory 路径
\end{itemize}

\textbf{输出：}
\begin{itemize}
  \item \texttt{result.json}
  \item \texttt{summary.csv}
  \item \texttt{plots/}（effective mass、fit stability 等）
  \item \texttt{run.log}
  \item \texttt{manifest.json}
\end{itemize}

\textbf{可以自动做：}
\begin{itemize}
  \item 读取 config、检查路径和文件是否存在
  \item 运行已有 notebook / script / CLI
  \item 把 notebook 重构成 Python CLI
  \item 生成结构化输出文件
  \item 修 bug、写 pytest
  \item 写 missing analysis scripts
  \item 维护 repo skeleton
\end{itemize}

\textbf{不能做：}
\begin{itemize}
  \item 不决定 central fit
  \item 不决定是否接受物理结果
  \item 不修改 raw data
  \item 不覆盖 accepted results
  \item 不做大范围不可追踪 shell 操作
  \item 重大修改必须有 tests
\end{itemize}

\textbf{Month 1 最低实现：}config-driven CLI + Pydantic schema + pytest + 输出 manifest/result/log/plots。

\textbf{未来高级实现：}自动检测缺失的 analysis scripts 并用 Codex 生成；自动检测 pipeline 瓶颈；支持 HPC 批量提交。

\textbf{验收标准：}从 clean repo 运行一条命令复现 golden example；pytest 全部通过；能解释 config 和 result 中每个字段；Git 有 8--12 个小 commit。

\subsection{Agent 2：Correlator Analyst Agent（L2：数据与拟合分析）}

\begin{tcolorbox}[colback=gray!5,colframe=gray!50,title=真实科研组类比]
负责检查 correlator 数据质量的 postdoc / 高年级研究生。很多 LQCD 问题在 correlator 层面就已经能发现。
\end{tcolorbox}

\textbf{解决的问题：}在进入复杂拟合之前，先判断数据质量是否足够。plateau 是否存在？bootstrap 误差是否合理？signal-to-noise 退化是否严重？

\textbf{输入：}2pt correlator CSV / HDF5 文件 + config

\textbf{输出：}
\begin{itemize}
  \item \texttt{correlator\_diagnostics.json}
  \item \texttt{effective\_mass\_summary.csv}
  \item \texttt{correlator\_quality\_report.md}
  \item effective mass plots
\end{itemize}

\textbf{可以自动做：}
\begin{itemize}
  \item 计算 effective mass 并画图
  \item 检查 plateau 是否存在（基于数值判据）
  \item 检查 bootstrap / jackknife 误差是否合理
  \item 检查不同 momentum / $z$ / gamma channel 的数据覆盖
  \item 检查 real / imaginary part 是否有明显异常
  \item 标记 bad correlator 或 suspicious correlator
\end{itemize}

\textbf{不能做：}不做 fit（那是 Fit Strategy Postdoc 的工作）；不决定数据丢弃（只能标记 suspicious）。

\textbf{Month 1 最低实现：}基于现有 effective mass CLI，加入 plateau 自动检测和 basic statistics reporting。输出 \texttt{correlator\_diagnostics.json}。

\textbf{未来高级实现：}LLM-based correlator quality narrative；对比多个 ensemble 的 correlator 质量；自动检测异常 configuration。

\textbf{验收标准：}能对 golden example 生成 \texttt{correlator\_diagnostics.json}；能标记至少一个可疑 correlator（如果存在）；good case 和 bad case 的判断与导师一致。

\subsection{Agent 3：Fit Strategy Postdoc Agent（L2：数据与拟合分析）}

\begin{tcolorbox}[colback=gray!5,colframe=gray!50,title=真实科研组类比]
负责设计 fit 策略的 postdoc。不是自动 grid search 工具，而是提出少量有物理动机的 fit hypotheses。
\end{tcolorbox}

\textbf{解决的问题：}在给定 correlator diagnostics 后，如何选择 fit 方案？不是 brute-force scan 所有可能组合，而是提出 2--5 个有物理意义的候选方案。

\textbf{输入：}\texttt{summary.csv} + \texttt{correlator\_diagnostics.json}

\textbf{输出：}
\begin{itemize}
  \item \texttt{fit\_strategy\_plan.json}
  \item \texttt{fit\_candidates.csv}
  \item \texttt{fit\_strategy\_notes.md}
\end{itemize}

\textbf{输出示例：}
\begin{lstlisting}
{
  "recommended_fit_hypotheses": [
    {
      "name": "2state_default",
      "reason": "effective mass suggests excited-state contamination at small t",
      "tmin_range": [5, 7],
      "risk": "medium"
    },
    {
      "name": "1state_plateau_crosscheck",
      "reason": "late-time plateau appears stable but errors grow",
      "tmin_range": [8, 10],
      "risk": "medium"
    }
  ]
}
\end{lstlisting}

\textbf{可以自动做：}
\begin{itemize}
  \item 选择 1-state / 2-state / 3-state fit 的候选方案
  \item 选择 $t_{\min}$ / $t_{\max}$ / ratio window
  \item 判断是否需要 prior
  \item 比较 plateau fit、two-state fit、summation fit
  \item 检查 fit 是否 overfit 或 underfit（基于 $\chi^2$/dof 和参数灵敏度）
  \item 生成 2--5 个 high-value fit hypotheses
\end{itemize}

\textbf{不能做：}不搞 brute-force scan；不最终选定 central fit（那是 Analysis Coordinator 的工作）；不与 Critical Referee 争夺最终判断权。

\textbf{Month 2 最低实现：}rule-based module：读取 summary.csv，计算 tmin stability、model dependence sigma、chi2 quality。输出 \texttt{fit\_strategy\_plan.json}。

\textbf{未来高级实现：}LLM-based reasoning：从 effective mass 图和 correlator diagnostics 自动推理 fit 策略；学习先前 accepted cases 的 fit 选择模式。

\textbf{验收标准：}生成的 fit hypotheses 至少有 2 个；每个 hypothesis 都有物理理由；能在 3 个测试 case（good/ambiguous/bad）上输出合理的候选方案。

\subsection{Agent 4：Matrix Element Analyst Agent（L2：数据与拟合分析）}

\begin{tcolorbox}[colback=gray!5,colframe=gray!50,title=真实科研组类比]
负责 bare matrix element 中间分析的 postdoc / 高年级研究生。meson DA 分析的关键不只在于 2pt fit，更在于从 ratio 走向物理 DA。
\end{tcolorbox}

\textbf{解决的问题：}检查 bare matrix element 的 $z$-dependence、$P_z$-dependence、real/imag symmetry 和 normalization。这些中间量的质量直接决定最终 DA 的可信度。

\textbf{输入：}ratio fit 结果 + bare ME output + \texttt{fit\_strategy\_plan.json}

\textbf{输出：}
\begin{itemize}
  \item \texttt{matrix\_element\_diagnostics.json}
  \item \texttt{bare\_me\_summary.csv}
  \item \texttt{z\_dependence\_plots.pdf}
  \item \texttt{pz\_dependence\_plots.pdf}
\end{itemize}

\textbf{可以自动做：}
\begin{itemize}
  \item 检查 ratio fit 结果是否在统计误差内稳定
  \item 检查 bare ME 的 $z$-dependence 是否平滑
  \item 检查 $P_z$-dependence 是否合理
  \item 检查 local matrix element normalization
  \item 检查 real / imaginary symmetry
  \item 检查不同 fit strategies 是否给出一致的 bare ME
\end{itemize}

\textbf{不能做：}不决定哪个 bare ME 是最佳结果；不做 matching 到 light-cone DA（那是 Perturbative Matching Expert 的工作）。

\textbf{Month 2 最低实现：}rule-based module：读取 bare ME，检查 $z$-dependence 平滑度和 real/imag symmetry。输出 \texttt{matrix\_element\_diagnostics.json}。

\textbf{未来高级实现：}LLM-based analysis：自动描述 $z$-dependence 趋势和异常；对比不同 $P_z$ 下的 bare ME 一致性。

\textbf{验收标准：}能对 golden example 生成 \texttt{matrix\_element\_diagnostics.json}；能标记 $z$-dependence 中的异常点（如果存在）；输出图能清楚展示 real/imag 两部分。

\subsection{Agent 5：Critical Referee Agent（L4：批判与决策）}

\begin{tcolorbox}[colback=gray!5,colframe=gray!50,title=真实科研组类比]
合作组 internal referee。他的工作不是给好评，而是专门挑错。每个 analysis 在 promotion 之前都应该被 referee 严格审查。
\end{tcolorbox}

\textbf{解决的问题：}科学研究中最危险的错误不是计算错误，而是没有发现假设的漏洞。必须有专门的批判角色，从方法学角度寻找所有潜在问题。

\textbf{输入：}\texttt{fit\_strategy\_plan.json} + \texttt{matrix\_element\_diagnostics.json} + \texttt{summary.csv}

\textbf{输出：}
\begin{itemize}
  \item \texttt{critical\_referee\_report.json}
  \item \texttt{objection\_list.md}
\end{itemize}

\textbf{输出示例：}
\begin{lstlisting}
{
  "major_objections": [
    {
      "issue": "fit_window_selection",
      "claim": "The recommended tmin may be too early.",
      "evidence": "E0 shifts by 1.8 sigma between tmin=5 and tmin=7.",
      "requested_check": "Repeat with tmin>=7 and compare bare ME."
    }
  ],
  "minor_objections": [],
  "approval_recommendation": "revise_before_accept"
}
\end{lstlisting}

\textbf{可以自动做（基于规则检查）：}
\begin{itemize}
  \item 检查 plateau 是否是假 plateau（例如只有 1--2 个点"看起来平"）
  \item 检查 fit window 是否 cherry-picking
  \item 检查 2-state fit 是否参数太多（overfitting）
  \item 检查 prior 是否过强（posterior $\approx$ prior）
  \item 检查 ratio window 是否避开了坏点
  \item 检查 $P_z$ dependence 是否提示系统误差没控制
  \item 检查 $z$-dependence 是否有非物理振荡
  \item 检查 local matrix element 是否破坏 normalization
  \item 检查 conclusion 是否超过数据支持
\end{itemize}

\textbf{不能做：}不决定最终方案（只提 objection 和 requested check）；不替代 Analysis Coordinator 做综合判断。

\textbf{Month 2 最低实现：}rule-based module：10+ 条 check rules。每条 rule 检查一个具体问题。输出 structured objection JSON。

\textbf{未来高级实现：}LLM-based reasoning：生成自然语言的 referee report；从 memory 中检索类似 case 的 objection 模式。

\textbf{验收标准：}能在 good case 上给出 0 major objection；能在 ambiguous case 上给出至少 1 个 major objection 并有具体 evidence；能在 bad case 上正确给出 "revise\_before\_accept" 或 "reject"。

\subsection{Agent 6：Analysis Coordinator / PI Agent（L4：批判与决策）}

\begin{tcolorbox}[colback=gray!5,colframe=gray!50,title=真实科研组类比]
Professor / project leader。不做具体计算，但综合所有报告做决策：这个结果可以接受吗？需要重跑吗？需要升级到人类审批吗？
\end{tcolorbox}

\textbf{解决的问题：}多个 agent 产出了多种报告（diagnostics、fit strategy、matrix element checks、referee objections），需要有人综合所有信息做出决策。

\textbf{输入：}所有下游 agent 的输出 + \texttt{critical\_referee\_report.json}

\textbf{输出：}
\begin{itemize}
  \item \texttt{decision\_log.json}
  \item \texttt{coordinator\_summary.md}
  \item \texttt{next\_action\_plan.json}
\end{itemize}

\textbf{decision\_log.json 示例：}
\begin{lstlisting}
{
  "case_id": "l64c64a076_m140",
  "decision_type": "fit_recommendation",
  "candidate_fits": [...],
  "recommended_fit": "2state_tmin5_tmax15",
  "referee_flags": [...],
  "risk_level": "medium",
  "human_approval_required": true,
  "reasons": [
    "2-state fit is more stable than 1-state fit",
    "local matrix element passes sanity check",
    "Pz dependence needs human review"
  ],
  "targeted_rerun": {
    "needed": false,
    "reason": null
  }
}
\end{lstlisting}

\textbf{可以自动做：}
\begin{itemize}
  \item 汇总所有 agent 报告
  \item 按规则判定 risk level
  \item 生成 decision\_log
  \item 决定是否需要 targeted rerun
  \item 决定是否触发 Human Approval Gate
  \item 更新 case memory（accepted / rejected / pending）
\end{itemize}

\textbf{不能做：}
\begin{itemize}
  \item 不亲自写代码
  \item 不忽略 Critical Referee 的 major objection
  \item 不把 medium/high risk 结果自动标为 accepted
  \item 不绕过 Human Approval Gate
\end{itemize}

\textbf{Month 2 最低实现：}rule-based module：读取所有 agent 输出，计算 risk level，生成 decision\_log 和 next\_action\_plan。

\textbf{未来高级实现：}LLM-assisted reasoning：生成自然语言 summary；从 memory 中检索类似 case 的决策模式；自动生成 human-readable recommendation。

\textbf{验收标准：}能在 good case 上输出 low risk + 不触发 human approval；能在 ambiguous case 上输出 medium risk + human\_review\_recommended；能在 bad case 上输出 targeted rerun suggestion。

\subsection{Agent 7：Human Approval Gate（L4：Risk-Based Conditional Gate）}

\begin{tcolorbox}[colback=gray!5,colframe=gray!50,title=本质]
这不是一个"agent"，而是一个基于风险的、条件触发的审批机制。它是 exception path，不是 always-on sequential gate。
\end{tcolorbox}

\textbf{解决的问题：}AI agents 可以处理大量 routine work 和越来越多的 analysis decisions，但最终的科学责任在人类。Human Approval Gate 确保高风险、不可逆、paper-level 的决定有人类把关。

\textbf{触发条件：}仅当 Analysis Coordinator 判定 risk level 为 High 或 Critical 时触发。Low/Medium risk 不触发。

\textbf{系统端职责：}
\begin{itemize}
  \item 判断何时触发（基于 risk level）
  \item 生成完整 approval packet（7 个文件，见 Ch.3）
  \item 在人类返回决定前将结果保存在 pending 状态
  \item 解析 \texttt{07\_human\_decision.yaml} 并更新 state / decision log / memory
  \item 超时未回复按 fallback 处理（默认 hold\_and\_remind）
\end{itemize}

\textbf{人类端职责：}
\begin{itemize}
  \item 审批 central fit 选择
  \item 审批 data rejection
  \item 审批 systematic uncertainty
  \item 审批 accepted result promotion
  \item 审批 paper-level conclusion
  \item 否决 AI 推荐时注明理由（供 memory 学习）
\end{itemize}

\textbf{Month 3 最低实现：}生成结构化 approval packet；读取 human decision YAML；在有/无人类决定的情况下正确更新 state。

\textbf{未来高级实现：}交互式 Web UI；邮件 / Slack 通知；decision deadline 自动提醒；人类决策模式统计。

\textbf{验收标准：}high-risk case 自动生成 approval packet；无 human decision 时 state 正确停留在 pending；人类决策被正确解析并推进 state。

\subsection{Agent 8：Analysis Memory Curator（L5：长期学习）}

\begin{tcolorbox}[colback=gray!5,colframe=gray!50,title=真实科研组类比]
负责记录经验教训的组内成员。不产出当次分析的结果，但让下一次分析更高效。
\end{tcolorbox}

\textbf{解决的问题：}没有 memory 的系统每次分析都从零开始。Memory Curator 把每次分析的 accepted/rejected/failed cases 结构化保存，让系统逐步积累经验。

\textbf{输入：}decision\_log + human feedback + agent 输出路径

\textbf{输出：}
\begin{itemize}
  \item \texttt{memory/accepted\_cases.yaml}
  \item \texttt{memory/rejected\_cases.yaml}
  \item \texttt{memory/pending\_cases.yaml}
  \item \texttt{memory/failure\_patterns.md}
  \item \texttt{memory/memory\_update\_log.json}
\end{itemize}

\textbf{可以自动做：}
\begin{itemize}
  \item 保存 accepted / rejected / failed cases
  \item 总结失败原因（基于 Critical Referee flags）
  \item 把 human feedback 写入对应 case
  \item 检索类似 case 供 Analysis Coordinator 参考
\end{itemize}

\textbf{不能做：}不覆盖人类决定；不删除历史记录。

\textbf{Month 3 最低实现：}YAML / JSON 文件存储；basic 检索（按 ensemble、momentum、risk level）。

\textbf{未来高级实现：}SQLite / DuckDB 存储；RAG 检索；自动生成 failure pattern summary；为相似 case 提供 prior fit strategy recommendation。

\textbf{验收标准：}每个 case 结束后 memory 自动更新；能通过命令行检索过往 cases；accepted/rejected/pending 三类 cases 分开保存。

\section{工具、职责与选型理由}

本章按\textbf{功能}组织工具介绍，而不是按工具名堆砌。每个工具回答三个问题：\textbf{它解决什么问题？本项目什么时候用？学生最低需要掌握什么？}

\subsection{Reproducible Analysis：config、schema 与结构化输出}

\textbf{解决的问题：}科研分析不能依赖 notebook 里的手动路径和手动保存。可复现分析的基石是 config-driven pipeline + typed schema + structured output。

\textbf{核心工具：}
\begin{itemize}
  \item \textbf{Python CLI}：所有分析通过命令行启动，参数来自 config 文件。例：\texttt{python -m lqcd\_agent.analysis.run --config configs/l64c64a076\_m140.yaml}
  \item \textbf{Pydantic}：定义 config schema 和 result schema。所有输入输出都是 typed、validated、self-documenting。
  \item \textbf{YAML / JSON / CSV}：config 用 YAML（人类可读），result 用 JSON（机器可读），summary 用 CSV（表格分析）。
\end{itemize}

\textbf{使用时序：}Month 1 Week 2（CLI + schema）、贯穿全部三个月。

\textbf{学生最低需要掌握：}能写一个 Pydantic BaseModel；能用 argparse 或 click 写 CLI entry point；能解释为什么 config 必须包含所有影响结果的参数。

\textbf{不要求一开始掌握：}复杂的 Pydantic validator；nested generic types；async CLI。

\subsection{Testing：pytest}

\textbf{解决的问题：}Codex 生成的代码不能直接信任。pytest 把关键行为固定为可回归的测试，防止后续修改无声破坏已有功能。

\textbf{核心工具：}pytest + tmp\_path（临时目录测试）

\textbf{使用时序：}Month 1 Week 2 开始写 config validation test；Week 3 加入 CLI smoke test 和 output existence test；Month 2--3 持续扩展。

\textbf{学生最低需要掌握：}能写 smoke test、unit test、regression test；能用 tmp\_path 避免测试污染真实输出。

\textbf{不要求一开始掌握：}fixture factories；parametrize；mocking；coverage reports。

\subsection{Scientific Workflow：Snakemake}

\textbf{解决的问题：}分析有多个步骤，步骤之间有文件依赖。改了一个参数后，不知道哪些步骤需要重跑。Snakemake 管理文件依赖 DAG，只重跑需要更新的步骤。

\textbf{为什么选 Snakemake 而不是 Dagster/Prefect：}
\begin{itemize}
  \item Snakemake 专为 scientific file-driven workflow 设计（raw data $\to$ result $\to$ plot $\to$ summary）
  \item 用 Python 风格规则，适合 LQCD 学生逐步学习
  \item 原生支持 HPC 环境（Slurm、Condor 等）
  \item Dagster/Prefect 更偏数据工程平台，对文件型科研流程过重
\end{itemize}

\textbf{使用时序：}Month 2 Week 5 引入。

\textbf{学生最低需要掌握：}能写 rule（input/output/shell）；能理解 dependency-aware rerun；能用 \texttt{--dry-run} 检查计划；能把已有 CLI 包装成 Snakemake rule。

\textbf{不要求一开始掌握：}checkpoint files；wildcards；复杂的 HPC profile；conda integration。

\subsection{Agent Orchestration：LangGraph（或 Python State Machine）}

\textbf{解决的问题：}多个 agent 之间如何传递状态？如何在正确节点暂停等待人类审批？如何在 rerun 后恢复状态？LangGraph（或等价 state-machine）管理 agent 决策 DAG。

\textbf{为什么选 LangGraph：}
\begin{itemize}
  \item 适合 stateful multi-agent workflow
  \item 支持 durable execution（状态持久化）
  \item 支持 human interrupt / resume
  \item agent 流程表示为清晰 graph，不是不可追踪的长聊天
\end{itemize}

\textbf{与 Snakemake 的分工：}
\begin{center}
\begin{tabular}{p{0.22\linewidth}p{0.36\linewidth}p{0.32\linewidth}}
\toprule
工具 & 负责什么 & 不负责什么 \\
\midrule
Snakemake & 科学计算 workflow、文件依赖、增量重跑、HPC 批量执行 & 不负责 agent reasoning 和 human approval 对话 \\
LangGraph & 多 agent 状态流、判断节点、人工中断、targeted rerun、memory update & 不负责底层文件依赖和大规模批处理 \\
\bottomrule
\end{tabular}
\end{center}

即：\textbf{Snakemake 管数据分析 DAG，LangGraph 管 agent 决策 DAG}。

\textbf{使用时序：}Month 3 Week 9 引入。Month 2 可以先用简单的 Python state machine。

\textbf{学生最低需要掌握：}能定义 typed state；能写 node 函数；能用 conditional edge；能保存/恢复 graph state。

\textbf{不要求一开始掌握：}LangGraph 全部高级API；streaming；checkpoint 高级配置。

\subsection{Memory：从 YAML 到 SQLite/DuckDB/RAG}

\textbf{解决的问题：}没有 memory，每次分析都从零开始。memory 保存结构化经验（不只是聊天记录）。

\textbf{演进路线：}
\begin{itemize}
  \item \textbf{Month 1--2：}不需要独立的 memory 模块。output 目录 + \texttt{decision\_log.json} 即为初始 memory。
  \item \textbf{Month 3：}YAML / JSON 文件存储（\texttt{accepted\_cases.yaml} 等）。
  \item \textbf{未来：}SQLite / DuckDB（支持检索和统计）+ RAG（让 agent 读取历史 decisions）。
\end{itemize}

\textbf{学生最低需要掌握：}能定义 memory entry schema；能写入/读取 YAML；能按 case\_id 检索。

\subsection{Observability：run.log、decision\_log.json 与未来 tracing}

\textbf{解决的问题：}系统运行后，如何回答"上一步发生了什么？为什么做了这个决定？哪里最常失败？"

\textbf{当前方案：}
\begin{itemize}
  \item \texttt{run.log}：命令、返回码、运行时间、错误
  \item \texttt{manifest.json}：config hash、git commit、timestamp、输出文件列表
  \item \texttt{decision\_log.json}：每次 decision 的理由、证据、风险等级
\end{itemize}

\textbf{未来方案：}MLflow 或 OpenTelemetry 风格 tracing，记录每个 node 耗时、LLM 调用成本、失败率分布。

\subsection{AI-Assisted Development：Codex}

\textbf{解决的问题：}学生不应该手工写每一行代码。Codex 辅助生成 repo skeleton、CLI、schema、tests、Snakemake rules、agent nodes。

\textbf{使用时序：}贯穿全部三个月。每天一个小任务，Codex 生成初版 $\to$ 学生检查 $\to$ 运行 pytest $\to$ Git commit。

\textbf{学生最低需要掌握：}能写结构化 prompt（见 Part VI Ch.11）；能用 traceback 让 Codex 修 bug；能检查 Codex 代码的正确性和安全性。

\textbf{Codex 不应该直接决定：}central fit、数据丢弃、systematic uncertainty、accepted result promotion、paper-level physical conclusion、未经测试的大范围重构。

\textbf{学习目标：}能把 Month 2 的模块封装成 state machine nodes，实现结构化状态传递。

\textbf{任务：}定义 AgentState（TypedDict）→ 封装已有模块为 node 函数 → 实现线性 graph → 保存 graph\_state.json。

\textbf{AgentState 关键字段：}
\begin{lstlisting}[language=Python]
class AnalysisAgentState(TypedDict):
    case_id: str
    status: str                         # "running" | "success" | "failed" | "needs_human_approval"
    risk_level: str                     # "low" | "medium" | "high" | "critical" | "unknown"

\subsection{Week 10：Human Approval Gate + Case Memory}

\textbf{学习目标：}实现 risk-based conditional gate：Analysis Coordinator 后根据 risk level 走不同分支。

\textbf{任务：}实现条件分支逻辑 → 生成 approval packet（7 文件）→ 解析 human decision YAML → 更新 case memory。

\textbf{条件分支逻辑：}
\begin{lstlisting}[language=Python]
if risk_level == "low":
    auto_continue()          # 自动推进
    write_decision_log()
    memory_update("accepted")
elif risk_level == "medium":
    continue_as_pending()    # 标记 pending
    write_decision_log()
    memory_update("pending")
elif risk_level == "high":
    generate_approval_packet()
    await_human_decision()   # 暂停，等待审批
elif risk_level == "critical":
    halt_and_notify_pi()     # 禁止推进
\end{lstlisting}

\textbf{输出：}\texttt{approval\_packet/}（7 个文件）、\texttt{memory/accepted\_cases.yaml}、\texttt{memory/rejected\_cases.yaml}、\texttt{memory/pending\_cases.yaml}

\textbf{导师检查：}high risk case 是否生成 approval packet？无 human decision 时 state 是否停留在 "needs\_human\_approval"？medium risk 结果是否不自动进入 accepted？

\textbf{常见错误：}把 Human Approval Gate 当成 always-on gate → 它只在 high/critical risk 触发。

\subsection{Week 11：Evaluation Harness + Final Report 自动生成}

\textbf{学习目标：}能用固定的 evaluation cases 测试 agent 决策稳定性，能自动生成 human-readable report。

\end{itemize}

  3. model dependence (1-state vs 2-state sigma difference)
  4. fit failure rate
- Write fit_strategy_plan.json with 2-5 recommended hypotheses
- Each hypothesis must have a physics reason (not just "lowest chi2")
- Do NOT output a brute-force grid scan of all possible tmin combinations

Add tests for stable case, large chi2 case, and model-dependence case.
\end{lstlisting}

\textbf{禁止事项：}不允许做 grid scan；不允许不写物理理由就推荐 fit。

\textbf{验收标准：}生成的 hypotheses 有物理理由；每个 case 2--5 个候选；测试覆盖 3 种情况。

\subsection{练习 7：写 Critical Referee Objection Logic}

\textbf{目标：}让 Codex 实现反对意见检查规则。

\textbf{输入：}fit\_strategy\_plan.json + summary.csv 的字段

\textbf{Codex prompt：}
\begin{lstlisting}
Task:
Implement Critical Referee checks in:
`src/lqcd_agent/critical_referee/critical_referee.py`

The referee must find problems, not give compliments. Implement at least 10 check rules:

1. False plateau detection (plateau has <3 stable points)
2. Fit window cherry-picking (selected tmin is suspiciously narrow)
3. Overfitting check (2-state has many more params but similar chi2/dof to 1-state)
4. Prior dominance check (posterior ~= prior within 0.5 sigma)
5. Tmin sensitivity check (E0 shifts > 2 sigma across tmin values)
6. Pz-dependence anomaly (trend reverses after normalization)
7. Z-dependence non-smoothness (oscillations in z-space)
8. Local ME normalization violation (z=0 value deviates from 1 by >3 sigma)
9. Real/imag symmetry violation
10. Conclusion overreach (claim stronger than data supports)

Output: critical_referee_report.json with major_objections[] and minor_objections[].
Each objection must have: issue type, claim, evidence (specific numbers), requested_check.

Add tests for good case (0 major objections), ambiguous case (1-2 major objections), 
and bad case (>=3 major objections or recommend reject).
\end{lstlisting}

\textbf{禁止事项：}不允许只输出"看起来不错"的结论；不允许没有 evidence 的 objection。

\textbf{验收标准：}good case 上 0 major objection；ambiguous case 上至少 1 个有数字 evidence 的 objection。

  06_decision_options.yaml          # structured options with risk_if_chosen

The 06_decision_options.yaml must include:
- case_id, risk_level, question
- ai_recommendation with preferred option and reason
- 2+ options, each with label, risk_if_chosen, and ai_preference
- deadline
- fallback_if_no_response: "hold_and_remind"

Add test that generates a complete approval packet from mock data.
\end{lstlisting}

\textbf{禁止事项：}不允许 hard-code 具体 case 信息；不允许生成空文件。

\section{未来升级方向：如何变成更高级的系统}

三个月后，如果原型成功，以下是逐步升级的方向。核心理念不变：\textbf{AI agents 逐步承担更多 routine labor 和 analysis decisions；人类保留 high-value decision making 和 final accountability。}

\subsection{升级路线图总览}

\begin{center}
\begin{tabular}{p{0.22\linewidth}p{0.35\linewidth}p{0.33\linewidth}}
\toprule
升级方向 & 从（Month 3 状态） & 到（长期目标） \\
\midrule
Analysis Coordinator & rule-based & LLM-assisted reasoning + guardrail \\
Critical Referee & single referee & multi-agent debate（proponent vs alternative vs referee） \\
Memory & YAML / JSON & SQLite / DuckDB / vector database / RAG \\
Agent 规模 & single case & ensemble-level campaign \\
LQCD Physics Expert & basic rule-based checks & LLM-based LQCD physics reasoning \\
Perturbative Matching Expert & 暂不实现 & quasi-DA $\to$ light-cone DA 全流程 \\
Observability & run.log + decision\_log & MLflow / OpenTelemetry tracing + dashboard \\
Human Approval & file-based approval packet & interactive review UI + notification \\
AI Development & Codex-assisted coding & semi-autonomous research engineering loop \\
Physics goal & golden / fake example & real production DA analysis \\
\bottomrule
\end{tabular}
\end{center}

\subsection{升级 1：从 Rule-Based 到 LLM-Assisted Analysis Coordinator}

第一版 Analysis Coordinator 使用规则是正确选择（透明、可测试、可控）。下一步引入 LLM：
\begin{itemize}
  \item LLM 读取 structured diagnostics，生成 human-readable reasoning
  \item LLM 提出 candidate explanations 和 targeted rerun plan
  \item Rule-based guardrail 检查 LLM 输出是否符合 schema 和安全规则
  \item 中高风险结论仍需 human approval
\end{itemize}

\subsection{升级 2：从 Single Referee 到 Multi-Agent Debate}

引入多个 reviewer 角色，模拟真实合作组的内部讨论：
\begin{itemize}
  \item Fit Strategy Postdoc A（proponent）：提出主方案
  \item Fit Strategy Postdoc B（alternative）：提出备选方案
  \item Critical Referee：寻找不稳定点和漏洞
  \item Lattice QCD Physics Expert：检查整体物理趋势
  \item Perturbative Matching Expert：检查 matching/factorization 相关系统误差
  \item Analysis Coordinator：综合各方意见，做出决策
\end{itemize}

每个 reviewer 必须输出结构化 JSON（含 blocking\_issues、non\_blocking\_warnings、recommended\_action、confidence、evidence\_files），以保证 debate 可测试、可记录、可复现。

\subsection{升级 3：从 YAML Memory 到 SQLite/DuckDB + RAG}

当 case 数量超过几十个时，YAML 检索不便。升级路径：
\begin{itemize}
  \item SQLite / DuckDB 存储 structured case records
  \item 支持按 ensemble、momentum、risk level、failure pattern 检索
  \item RAG 让 agent 从历史 cases 中检索相似情况和 prior decisions
  \item 自动生成 failure pattern summary 和常见 risk 统计
\end{itemize}

\subsection{升级 4：从 Single Case 到 Ensemble-Level Campaign}

扩展到多个 ensemble、多个 momenta、多个 $z$ values：
\begin{itemize}
  \item 自动生成 campaign config
  \item Snakemake 批量调度所有 cases
  \item Campaign-level Analysis Coordinator 检查 ensemble dependence、$P_z$ dependence、$z$-dependence
  \item 生成 campaign summary report
\end{itemize}

\subsection{升级 5 \& 6：加入 LQCD Physics Expert 和 Perturbative Matching Expert}

从 Month 3 的 basic rule-based checks 升级为完整的 LLM-based 物理审查：
\begin{itemize}
  \item Lattice QCD Physics Expert：检查 discretization effects、finite-volume effects、excited-state contamination、ensemble consistency
  \item Perturbative Matching Expert：检查 matching kernel、renormalization scheme、factorization scale、endpoint behavior
\end{itemize}

\subsection{升级 7 \& 8：Observability + Interactive Review}

\begin{itemize}
  \item MLflow 或 OpenTelemetry tracing 记录每个 node 的耗时、LLM 调用成本、失败率
  \item Dashboard 展示 analysis DAG、agent graph、decision log、plots
  \item Human Approval 从 file-based 升级为交互式 Web UI（通知 + 一键审批 + 批注）
\end{itemize}

\subsection{最终理想形态：LQCD Analysis Subgroup as Code}

最终目标不是做一个"更聪明的 chatbot"，而是把整个 LQCD meson DA 分析流程变成一个\textbf{可审计、可复现、可学习的 AI analysis subgroup}。

在这个理想系统中：
\begin{quote}
导师提出物理目标（例如"在 ensemble A 上分析 pion DA，检查 fit stability、bare ME systematics 和 matching uncertainty"），系统自动组织分析流程、运行计算、检查质量、发现异常、提出少量高价值判断和 rerun 建议，并把所有代码、数据、图、日志、决策和人工审批保存下来。AI agents 自动承担大部分 routine labor 和越来越多的 routine analysis decisions；人类主要提出 physics goal、检查关键 evidence、审批高风险结论，并对最终科学结论负责。
\end{quote}

这就是本项目的核心愿景：\textbf{用 AI agents 构建一个像真实 LQCD 分析子组一样工作的科研系统，把人类从重复劳动中解放出来，让人类专注在只有人类能做的判断上。}

\textbf{本章交付清单：}
\begin{itemize}
  \item 能说出至少 5 个未来升级方向；
  \item 能解释从 rule-based 到 LLM-assisted 的渐进策略；
  \item 能描述"LQCD Analysis Subgroup as Code"的理想形态。
\end{itemize}

\section*{附录 B：参考资料与工具选择依据}
\addcontentsline{toc}{section}{附录 B：参考资料与工具选择依据}

\begin{itemize}
  \item Snakemake 适合 reproducible and scalable scientific data analysis，尤其适合文件依赖清楚的科研 workflow。
  \item LangGraph 适合 stateful agent workflow、durable execution 和 human intervention interrupt / resume。
  \item TradingAgents 类系统体现了 specialized roles、debate、risk management 和 final decision gate 的 multi-agent 设计思想。

  \item Nextflow 在容器化、跨平台、标准化大 pipeline 中很强，但对当前 Python-heavy、LQCD exploratory analysis 来说，Snakemake 更适合。
\end{itemize}
